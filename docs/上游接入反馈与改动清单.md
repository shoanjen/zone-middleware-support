# 上游接入反馈与改动清单

> 来源：`zone-boot-template`（上游模板项目）接入实践反馈 · 2026-11-22
> 适用版本：`com.zone.middleware:1.0.0-SNAPSHOT` · 关联手册：《接入手册》

## 背景

zone-boot-template（DDD 六模块模板，本工作区项目）自 2026-11-21 起全量接入本二方包，接入期间对包能力提出过 8 条反馈，**其中 3 条 P1（全局异常处理器 `zone-middleware-web` 模块、ZoneHttpTemplate TypeReference 重载、Trace 入站 Filter）与 5 条 P2（手册 §3.3 DDD 分层建议、§2 spring-tx 标注、自定义错误码章节、Redis 原语、BaseRequest.sign 废弃说明）已全部落地**（见手册 §3.3 / §10 及对应章节）。

本文档为**剩余 3 条 P3 改动清单**，供排期实施；每条给出问题、涉及文件、改法与验收标准。另附一条设计决策记录（已否决方案）。

## 改动 1（P3-1，建议立即）· advice 补 `ConstraintViolationException` 处理

### 问题

`ZoneGlobalExceptionAdvice`（`zone-middleware/zone-middleware-web/src/main/java/com/zone/middleware/web/advice/ZoneGlobalExceptionAdvice.java`）现只显式处理 `BindException` / `MethodArgumentNotValidException`（@RequestBody / 表单绑定校验）。当上游 Controller 使用**方法级校验**（类上 `@Validated` + `@RequestParam @NotBlank` 等）时，Spring 抛出的是 `jakarta.validation.ConstraintViolationException`——当前未被显式捕获，落兜底 `SYS-9999`（应为 `BIZ-4001`）。上游项目一旦使用方法级校验即踩坑。

### 涉及文件与改法

| 文件 | 改动 |
|---|---|
| `zone-middleware/zone-middleware-web/pom.xml` | **main 编译期需要 jakarta.validation-api**：现 `spring-boot-starter-validation` 仅 test scope（L73-77），main 代码 import 不可用。新增 compile 依赖 `jakarta.validation:jakarta.validation-api`（版本随 Boot BOM；纯 API 无实现，不向无校验场景传递 provider，保持「能力默认关」精神） |
| `ZoneGlobalExceptionAdvice.java` | ① 新增 import `jakarta.validation.ConstraintViolationException`；② 在 `handleBindException` 后新增：`@ExceptionHandler(ConstraintViolationException.class)`，violations 取第一条拼 `v.getPropertyPath() + " " + v.getMessage()`（与 handleBindException 的「字段 + 空格 + 提示」格式一致），无 violation 时回退 `BusinessError.PARAM_INVALID.getMessage()`，返回 `ZoneResult.fail(BusinessError.PARAM_INVALID, message)`；③ 类 javadoc「三类异常」改为「四类异常」并补方法级校验描述 |
| `ZoneGlobalExceptionAdviceTest.java` | 补 2 个用例（沿用现有 @SpringBootTest + MockMvc + probe controller 模式）：probe controller 类加 `@Validated`，新增端点 `GET /advice/param?orderNo=`（参数 `@NotBlank(message = "不能为空")`）→ 断言 BIZ-4001 且 message 含 `orderNo`；多字段违规时取第一条 |
| `docs/接入手册.md` §10.1 | `exception-advice-enabled` 说明补「方法级校验异常（`ConstraintViolationException`）同样转 `BIZ-4001`（字段路径 + 提示）」 |

### 验收

- 中间件 `mvn clean install` 全绿（新增用例过）；
- 上游 `@Validated` 方法级校验失败返回 `BIZ-4001` 而非 `SYS-9999`；
- 既有 BindException 路径行为不变。

## 改动 2（P3-2，可选）· reqId 随机段长度可配置

### 问题

`ZoneTraceInboundFilter.newReqId()` 固定 8 位随机段（`"r-" + UUID 前 8 位`），碰撞空间 16⁸ ≈ 43 亿——日常 QPS 足够，高并发/长窗口聚合场景不可调。traceId 已含时间戳前缀（`t-{yyyyMMddHHmmss}-{8位}`）无此问题，**长度配置仅作用于 reqId**。

### 涉及文件与改法

| 文件 | 改动 |
|---|---|
| `ZoneWebProperties.java` | 新增 `private int reqIdLength = 8;`（键：`zone.middleware.web.req-id-length`） |
| `ZoneWebInboundAutoConfiguration.java` | `zoneTraceInboundFilterRegistration()` 改 `new ZoneTraceInboundFilter(properties.getReqIdLength())` |
| `ZoneTraceInboundFilter.java` | 加 `private final int reqIdLength;`；保留无参构造委托 `this(8)`（兼容现有调用/测试）；int 构造器校验 `8 ≤ reqIdLength ≤ 32`，越界抛 `IllegalArgumentException`（fail-fast，消息含允许范围）；`shortRandom()` 泛化为 `randomSegment(int length)`（UUID hex 共 32 位，覆盖 8–32 取段）；`newReqId()` 用 `randomSegment(reqIdLength)`，`newTraceId()` 保持 8 位不变 |
| `ZoneTraceInboundFilterTest.java` | 补 2 用例：reqIdLength=16 时 reqId 随机段为 16 位；越界（如 4）构造抛 IllegalArgumentException |
| `docs/接入手册.md` §10.1 | 表加一行：`zone.middleware.web.req-id-length` · 默认 8 · 「reqId 随机段长度，范围 8–32，越界启动失败；仅 trace-filter 开启时生效」 |

### 验收

- 默认值 8 时行为与现状完全一致（`r-` + 8 位）；
- 配 16 后日志 reqId 段为 16 位；越界配置启动失败。

## 改动 3（P3-3，可选·破坏性，SNAPSHOT 期可立即做）· 移除 `BaseRequest.sign` 字段

### 前置核实（2026-11-22 已完成）

全二方包源码对 `BaseRequest.sign` **零读取**（grep 命中的 `getSign()` 均为 `ZoneSecurityProperties.Sign` 配置项，与该字段无关）；签名校验唯一来源是请求头 `Zone-Access-Token`。删除无代码风险，仅上游存量报文兼容影响——当前全部构件为 1.0.0-SNAPSHOT 未发版，现在移除可免版本 bump 与废弃期滞留。

### 涉及文件与改法

| 文件 | 改动 |
|---|---|
| `zone-middleware-common/src/main/java/com/zone/middleware/common/request/BaseRequest.java` | 删除 L53-61（`@Deprecated private String sign` 字段及其 javadoc）；类 javadoc 中「时间戳与签名字段」措辞同步去掉「与签名」 |
| `docs/接入手册.md` L204（§4.3 字段清单） | 字段清单删去 `sign`，「（**sign 已废弃**……后续版本移除）」改为「（**sign 已于本版本移除**，签名一律经请求头 `Zone-Access-Token`）」 |

## 设计决策记录（2026-11-22 · 已否决）

**否决：公共参数 `BaseRequest` 增加 token 传参。** 凭证类字段统一走请求头（`Zone-Auth-Token`），理由：

1. **GET 无请求体**：签名体系支持 GET 端点，token 进 body 后 GET 无处承载；退至 query string 泄露面更大（URL 进网关日志 / Referer / 浏览器历史）；
2. **泄露面**：body 会被网关 / APM / 调试日志整包记录，且本包 `ZoneLog` 对对象参数按 fastjson2 JSON 渲染——Req 携带 token 后 `ZoneLog.info("{}", req)` 即把凭证写入日志常态；header 是生态惯例凭证通道（OAuth `Authorization: Bearer` 同位）；
3. **方向倒退**：本包已将 `sign` 从 body 迁至 `Zone-Access-Token` 请求头（§9.1），「凭证不进公共参数」是既定设计决策，token 进 body 与之相悖；
4. **协议搅动**：body 字段参与签名拼串（参数升序 `k1=v1`），token 混入需新增剔除规则；header 通道与签名完全隔离。

特殊客户端（无法设 header）场景的正解：网关侧读取约定 body 字段提升为 `Zone-Auth-Token` 请求头后转发。如需给上游口子，可将 `ZoneAuthTokenResolver`（现为 final 静态工具类）改造为接口 + `@ConditionalOnMissingBean` 装配，支持「header 优先、body 兜底」自定义解析——未列入本清单，仅备忘。
